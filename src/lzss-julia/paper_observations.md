# LZSS observations

- **RQ1 — Fidelity:** all 20 full 156,165,962-byte captures match exactly, including the real 50 MB source file, complete codec state/live streams, actual input readbacks, padded decoder output and guards. An independently structured CPU stream parser establishes losslessness; already-quantized input does not establish the upstream physical error bound or optimal compression.
- **RQ2 — Feedback and effort:** CUDA.jl needed a host-copy API repair before its first authored-device JIT; KA and JACC passed their first actual programs. JACC also had a Python generator setup rejection before Julia. Each backend submits one five-kernel bundle; mathematical/helper and host-harness reuse is explicit. Actual token windows retain cache/context and CUDA.jl END metadata undercoverage, excluded from calibration.
- **RQ3 — Execution:** means of trials 2–5 are native 3.830385 ms, CUDA.jl 4.851716 ms, KA 5.052416 ms, JACC 5.949182 ms for the six-case compression-plus-decompression pipeline. Separate subregion samples remain available. This named integration/resource-adapted study is excluded from untouched-native comparisons.
- **RQ4 — Mechanisms:** target CUB replacement, hierarchical-scan launch/scratch policies, explicit byte shared access and JACC shared-template requests confound frontend effects. No profiler counters or measured roofline position. All three targets use framework device kernels, without foreign device intrinsics or computed-result-driven host control.
- **RQ5 — Selection:** all three abstractions can express this complete integer codec. Choosing authored portable scans versus vendor scan integration is a separate implementation decision; observed timings do not prove a framework capability limit or universal preference.
