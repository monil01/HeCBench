# Stream-ordered allocation: three actual runtime policies

This NVIDIA sample demonstrates GPU memory allocation lifecycle. The numerical consumer is Float32 vector addition; the scientific use case is a temporary-buffer pattern, not a simulation model. Historical Julia contains genuine vector addition, but its three labeled cases all call the same CuArray allocation helper. The original source and Makefile are archived byte for byte; the new reference restores the actual runtime policies rather than treating equal numerical outputs as proof of equal allocator behavior.

The study uses unchanged native vectorAddGPU and three source-shaped100-repeat pipelines: traditional cudaMalloc/free with blocking copies and null-stream launch; cudaMallocAsync/freeAsync on an explicit nonblocking stream with release threshold0; and the same stream-ordered pipeline with UINT64_MAX retention threshold. The original ordering frees inputs after the kernel, copies the output, frees it, and synchronizes each async iteration. All Julia versions call the same actual system libcudart12.0.146 directly for allocation, copies, free and pool attributes. CUDA.jl owns the device kernel; KA and JACC use their own pure device indexing/dispatch, while the host runtime interoperability is explicitly CUDA specific. No other backend is certified. Nonowning CuArray wrappers only expose the actual runtime pointers; the Julia memory pool does not replace these allocations. Julia creates explicit streams through its driver API with the same nonblocking flag; native uses the runtime API.

Four named sizes1,255,257,4097 cover single-item, partial, full+tail and larger multipled-block cases. Inputs are bounded signed binary fractions. An independent integer-numerator oracle proves exact Float32 addition on this fixture. Every one of the100 full output vectors for each of12 paths is captured, not only a checksum or last iteration. Final-iteration actual GPU inputs are copied back before free and checked exactly. The source device allocations contain no guards; this study does not invent a guard-protection claim. All20 full1419889-word artifacts are identical, including9229 input-prefix values and1410660 states. Runtime status checks are fatal, short/missing fixture/oracle reads fail, and actual memory-pool support is queried.

The measured region is the full100-repeat allocation/H2D/add/free/D2H/free pipeline, summed across12 paths, with1200 kernel launches. Two extra final-iteration input-echo D2H copies are included in every model's region; all100 ordinary output copies target distinct preallocated host slots rather than overwriting one slot. Both are disclosed instrumentation covariates. Stream creation, pool setting and restoration, JIT/warmup, full independent checks and serialization are outside. Five checked trials retain all times and average2–5; each path has its own clock. The pool threshold is saved and restored. These small inputs do not establish original33554432-element allocation pressure or throughput. Full host/device times do not isolate kernel lowering, executed bandwidth, allocator internals, application benefit or roofline position. Native timing spikes remain in the required mean.

Two owned host-adapter repairs are retained separately from device translation: raw Ptr conversion needed UInt before the CuPtr constructor; explicit unsafe_destroy! left the registered stream finalizer and later double-destroyed a handle. The latter run produced one exact but rejected partial trial before failure. finalize(stream) now executes/removes the finalizer once. The vector-add kernel stayed unchanged: one CUDA.jl candidate, two compile/check invocations across three host processes, no device repair. KA/JACC each compile and pass their first candidate/check. Shared pipeline/oracle work is attributed once to reference preparation; subsequent model windows are ordered marginal costs and overlap the outer workflow, not exclusive billed or cold framework costs.
