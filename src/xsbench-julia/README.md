# XSBench: genuine continuous-energy event lookup

The native source identifies its event-based macroscopic cross-section lookup as a neutron-transport building block. It generates an energy/material query from a skip-ahead LCG, locates microscopic tabulation intervals, interpolates five reaction channels, and sums material concentration-weighted microscopic values. It writes only the1-based first-maximum channel label for verification. This is not a complete transport/history solver. Historical Julia was a placeholder index hash with unrelated summary/hardware literals, not a cross-section lookup; those original bytes remain archived.

## Faithful implementation and compiler feedback

NuclideGridPoint/XPoint is a matching48-byte, alignment8 AoS of sixFloat64 values; all actual buffer payloads remain256-byte aligned. Other arrays preserve source row-major material/index layouts. Each256-thread block has independent lookups with no atomics/shared memory/barriers; JACC explicitly allocates zero shared bytes. Portable device arithmetic/search/indexing uses its own framework and ordinary Julia, with CUDA host allocation/transfers/synchronization/readback only. Other GPU backends are unverified, and resource/cache/register/roofline explanations require profiling that this study has not collected.

The current CUDA.jl reference required three GPU candidates/check programs. Candidate1 failed B4InvalidIR because a mutable five-tuple accumulator was captured in an ntuple closure, producing unsupported dynamic indexing/arithmetic and tuple construction. A type-stable explicit tuple accumulation repaired that feedback. Candidate2 compiled, then raised a GPU exception in the hash path: Julia Int64(energy/du) requires an exact integer, whereas C++ assignment truncates. A CPU replay of the actual first hash query shows energy/du=4.366977495289336, native index4 and Julia InexactError. Explicit trunc(Int64,...) restored source semantics, and candidate3 passed all five checks. The failures, source revisions and CPU witness are preserved. First compilation success was candidate2; first verified success was3. No native or mathematical correction, tolerance change or failed-series replacement occurred.

KA and JACC each compiled/passed their first candidate/check after reusing that repaired shared algorithm. Each version has one primary plus one scientific observer entrypoint; check-program counts are not invented per-entrypoint JIT invocation counts. Shared physics/oracle/material preparation and repairs are credited once to reference work. Prospective windows include repeated/cached context, annotations, audits and coordination, overlap the workflow and describe ordered marginal effort. They cannot support intrinsic cold-start framework cost rankings or exclusive billed token totals; historical creation cost remains unknown.
