The source proof includes all four framework entries and common host orchestration, plus MPI/NCCL shims and launchers. Every contract uses physical5+6; there is no single-device semantic replacement. All20 current method barriers remain unresolved under current permission.

- **allreduce:** `study_native.cu::ring` / `study_common.jl::ring` completes CUDA-aware receive and `cudaDeviceSynchronize`/`CUDA.device_synchronize` before the add. `kernel_add` / own framework `add_kernel!` only accesses received temporary and local output chunk, with in-place output read/write. The final MPI exchange is initiated by the same host only after kernel completion. Native32×256 threads; CUDAjl32×256, KA8192 work items/group256 and JACC8192/grid32×256 preserve the same grid-stride arithmetic. MPI shim uses Irecv+Send+Wait for scatter and Sendrecv for gather. There is no peer-memory dereference, device polling or in-kernel host/MPI progress in the authored add. This supports conditional replay *of that kernel*, not arbitrary transport kernels. NCU must restore the in-place destination before every replay, and actual MPI/UCX compatibility and full five checks still need observed proof.
- **ccl:** the shim calls `ncclAllReduce(...ncclFloat,ncclSum...)`; native and Julia repeated loops both live outside vendor implementation. Private user send/recv buffers do not imply private vendor protocol state. NCCL's internal kernel algorithm/transport cannot be established from these host sources. `study_launch_bounded.py` has a90second original diagnostic limit: silently extending/disabling it for profiling is a new host-method adaptation and needs explicit prospective review, not tolerance for hanging processes.
- **p2p:** `remote()` runs after timed `exchange()` and readback/copy check. It first doubles remote source intoGPU6 target, then doubles that result back intoGPU5, synchronized between. Those kernels read peer-resident memory, so even their optional untimed diagnostic requires interconnect-aware interpretation; their counters cannot be labeled timed-copy work.
- **pingpong:** rank1 receives before increment and completes increment before send in warmup, but the timed loop only sends/receives. JACC additionally prepares its two increment callback specializations outside workflow trials; keep those source phases distinct. Timed NCCL kernels may synchronize with peer protocol and are not approved for ordinary one-rank replay here.
- **ring:** the timed closure is copies plus fences; Julia reset `fill!` occurs outside. A first sampled fill kernel would not certify timed arithmetic. Runtime copy implementation may involve device work; absence of authored kernels cannot settle that empirically.

## Installed tool support vs scientific safety

The hash-bound installed2022.4 help states that `--devices` selects profiling devices, `--target-processes application-only` selects the launched application, kernel replay replays individual kernels, and application replay relaunches the entire application and requires deterministic execution. Its application matching is per process/device, with strict matching available. These CLI capabilities do **not** prove GPU-device ordinal mapping, checkpoint completeness, collective protocol safety, cross-process synchronization behavior, or rank-independent arithmetic.

No claim is made that application replay automatically repairs NCCL profiling: a future method must preserve/re-establish both ranks, communicator state, concurrency and complete five checks, and demonstrate that the selected tool mode supports the vendor's execution dependencies. Range/application replay and rank-local placement are different experiments, not arbitrary replacements for a failed kernel replay. Installed help does not supply a ready-made collective-safe certificate.
